Map. design + how it scales

Real Apple Maps tiles under a sepia tint, custom paper-pin markers with serif uppercase city names, geodesic dashed routes. One source of truth; see the screenshot in "The five tabs" section above.

Why Apple Maps (not Google, not a static asset)

  • Privacy-aligned with Mailroom's "addresses stay private" stance. no third-party map opens leaking the user's IP to Google per session.
  • No API keys, no billing. works for any user instantly.
  • Real geography beats hand-drawn approximation. A real US coastline rendered by Apple looks better than my best SVG version of it.
  • Tradeoff accepted: Apple's labels ("NORTH AMERICA", "Toronto", "Maps Legal") bleed through the sepia tint. We mitigate with overlay decorations and a heavier tint. Acceptable for postcard-style decoration.

How this scales when you have lots of mail

The current screen is tuned for the first 5–10 friends and the first 20 cards. As Mailroom grows, here's what breaks and the plan for each:

MAP · BREAKS AT ~15 ROUTES
Routes overlap into spaghetti

Right now we draw 8 polylines and they sit pleasantly. At 15+ they cross each other constantly; at 50+ the dashed pattern becomes visual noise.

Fix: show only the N most-recent or most-active routes (top 12 by send count), aggregate the rest into a "+ 38 more" pill. Optionally fade older routes by recency so the visual hierarchy mirrors emotional hierarchy.

MAP · BREAKS AT ~25 CITIES
City label collisions

Two friends in NYC area = labels stack. Five friends in California = labels become unreadable. Currently we just render every label.

Fix: cluster nearby pins (Apple's MKClusterAnnotation equivalent in react-native-maps), show count on the cluster ("3"), tap to expand. Top tier of friends (most-active) keeps individual pin + label.

CONSTELLATION · BREAKS AT ~12 FRIENDS
Stars crowd the orbit ring

Current design places friends on a single 130pt circle. Six friends look balanced. Twelve start touching. Fifty would be illegible.

Fix: two orbital rings. inner ring for "close friends" (top 6 by send/receive count), outer ring for the next 12. Anyone beyond is a faint anonymous star in the background. The "Warmest Thread / Sleeping Stars" insight cards already surface specific friends; the constellation is decoration, not navigation.

SEND · BREAKS AT ~15 FRIENDS
Recipient cycler stops being fun

Right now you tap the recipient row to cycle to the next friend. Charming with 6 friends. Annoying with 30.

Fix: switch to a recipient sheet. tap → modal with search + recent contacts. Keep "cycler" affordance for users with ≤8 friends as a delightful detail.

FRIENDS · SCALES FINE
Rolodex is a list. handles any count

200 friends would scroll. Same UX. Maybe add a search bar at the top when count > 12. Maybe pin "recent contacts" to the top.

Fix: SectionList grouped by recency ("This month / Earlier"). Search bar above 12 friends. Optional: tap-to-sort.

MAIL HISTORY · SCALES FINE
Sheet is a paginated list. handles any count

200 sent cards = 200 list rows. Loads fine, scrolls fine. Eventually wants pagination (load 20 at a time) and filter by recipient/status/date.

Fix: already a FlatList with stable keys. Add a filter chip row + paging when count > 50.

MY CARD STATS · COSMETIC
Numbers get wide

"1,234" friends will overflow the 4-column row. We already have adjustsFontSizeToFit on the Map summary; same trick works here.

Fix: add the same numberOfLines={1}, adjustsFontSizeToFit pattern to MetricStrip. Cosmetic, not architectural.

CONTEXT CACHE · BREAKS AT ~500 ITEMS
AsyncStorage write-through gets slow

Every state change serializes the whole cache to AsyncStorage. At 500 postcards × 200 friends, JSON.stringify on every keystroke becomes laggy.

Fix: swap the bulk JSON cache for SQLite (via expo-sqlite), index by ID, only write what changed. Major architectural change but the right path at scale.

When to actually do this work

None of these matter for TestFlight beta. With 5–20 users and 10–50 sent cards across all of them, the current design works as-is. The right time to revisit scaling is when one specific user gets to 25+ friends. they'll be the first to feel the friction. Build the fix then. Premature scaling is the same trap as premature optimization.

The happy path

First-time user → first postcard sent.

  1. Welcome. step 1. Name + city + state. Skip-for-now available.
  2. Welcome. step 2. Email + password. Or "I already have an account" toggle to sign in. Forgot password link in sign-in mode.
  3. Free credits banner appears on My Card with the 5-credit gift. Subtle.
  4. My Card. Shows your monogram, tagline, QR for friends to scan, mail history entry.
  5. Send tab. Pick category (Note / Photo / Place / Custom). Compose. Pick recipient from rolodex. Tap Send.
  6. Cost is deducted server-side via the send_postcard RPC. Cache updates optimistically; rolls back on error.
  7. Success modal. Honest copy: "Sits in the queue until our printing partner is live." (Becomes real on Lob wire-up.)
  8. Mail history shows the new entry with status. Push notification fires when delivered.

What stayed the same on purpose

  • "Mail Card" as a product noun. that's the artifact inside Mailroom, like Tweets in Twitter. The card stays; the app is the room it lives in.
  • The Supabase project (nlwnmgwylmmnaemdnzlq.supabase.co). same DB, same auth, same tables.
  • Internal code symbols (MailClubContext, useMailClub, file paths). renaming these touches ~50 imports across 30 files and risks breakage. Safe to defer or land as a follow-up PR.
  • The project directory on disk (~/Downloads/mailclub-app). Xcode worktree path. You can mv it whenever you want; just update your shell shortcuts.

A real HTML page served by a Supabase Edge Function. No app install required. Mobile-friendly. Sender's address is never returned in the response. only their name + city, snapshotted at send time.

Privacy model

Sender sees
  • The status of their card: awaiting_address → queued → shipped → delivered
  • Whether the link has been opened
  • A push notification when the recipient claims
  • Never the recipient's address. RLS blocks it server-side.
Recipient sees
  • Sender's display name + city (frozen snapshot. survives sender's profile changes)
  • The postcard's handwritten message (preview)
  • A privacy-first address form
  • Never the sender's mailing address. It isn't returned by the API.

Under the hood

  1. send_postcard_via_claim() RPC. creates a row in postcard_claims with an 8-char base32 token (≈1.1T combinations, 30-day expiry, single-use) + a postcards row in awaiting_address status. Credits deducted atomically.
  2. Mobile app opens iOS Share.share() with the URL https://<project>.functions.supabase.co/claim?t=TOKEN + a pre-filled introductory message.
  3. GET /claim?t=TOKEN. Edge Function calls claim_lookup() RPC (service-role only). Renders mobile-friendly HTML with sender's name + city snapshot + message preview + address form.
  4. POST /claim?t=TOKEN. accepts JSON address. Calls redeem_postcard_claim() RPC. Marks claim claimed (single-use), flips postcard to queued.
  5. Next sprint: push notification to sender's phone → app captures postcard at print scale via react-native-view-shot → uploads + invokes lob-send-postcard. Card mails.
